# ADR 0012 — 库存账本、成本与过账边界

Status: Accepted for v0.6 implementation — 2026-09-05。用户阅读交付后回复“OK, 请继续”，按本文 D1–D6 建议施工；保留下文替代方案和限制供后续复核。

依据：[权威迁移上下文](../architecture/migration-context.md)第 4–7、9、12–18、23–26、40–46 节；具体施工见[库存 v0.6](../inventory-v0.6.md)，证据见[验收清单](../inventory-v0.6-acceptance.md)。

## 已确定且不重新设计的规则

沿用模块化单体、现有 RuntimeContext/事务/RLS/Audit/Outbox/幂等基础。库存由 InventoryEngine 集中处理，不可变 InventoryMovement 是事实源，InventoryBalance 是投影。禁止负库存；单据显式过账、不可改写、以新增冲销纠错；平均成本按移动加权计算；禁止 float 和后台异步核心过账。

原规范没有完全定义成本分组、历史冲销、占用流水形态、盘点并发策略和商品级阈值的仓库口径。下面是候选决策，不把“原文未说明”包装为已经存在的冲突。若评审改变候选方案，需同步调整施工规范、数据库约束及验收样例。

## D1. 按组织、仓库、商品计算移动平均成本

建议：成本与库存余额使用同一库存键。调拨按来源实际扣除金额转移，目标仓据此重算平均成本。Quantity/Price/UnitCost 为 NUMERIC(20,6)，Value 为 NUMERIC(20,4)，内部 Decimal 精度至少 50，ROUND_HALF_UP。

普通部分出库不改平均成本；全量出库扣完剩余金额并显式记录尾差，归零后保留最后平均成本供展示参考，下次入库重新计算。部分出库舍入后金额超过剩余金额则拒绝 COST_PRECISION_CONFLICT；零成本必须显式输入，空值不是零。

理由：与按仓库存锁及转移金额一致，规则可以通过流水重建。代价：同一商品在不同仓库可能不同成本；极小数量/金额的边界可能需要用户重新核对，不能偷偷截断出库金额。

评审替代：组织商品统一成本会引入跨仓共同成本状态及锁；更高单位成本精度或部分出库尾差分摊会改变精度/成本政策。不能在施工中无声切换。验收必须覆盖微小数量、六位成本舍入、金额极限及全量出库尾差。

## D2. 用统一不可变流水记录现有量与占用量变化

建议：Movement 保存 base_qty、reserved_qty_delta、value_delta。占用/释放是 base_qty=0 的专门流水类型，Reservation 为可重建的来源明细投影。对账同时验证现有量、占用量、金额及剩余占用总和。

理由：直接覆盖“所有库存变化产生流水”的硬约束；销售确认将来仍不改变现有量和成本。代价：流水页面需区分实物变化和占用变化；SUM(base_qty) 仍是实物库存事实。

评审替代：独立 ReservationEvent 账本也是可行设计，但需明确与“所有库存变化”的原文解释，不能只更新 reserved_qty 而无可重建事实。本阶段不增加销售单据或人工占用 API。

## D3. 只对各库存键最后一次操作执行整单冲销

建议：所有受影响库存键都没有后续流水时，按原数量、原金额和操作前平均成本恢复，新增冲销流水并保留原单/原流水。后续占用也视为依赖。调拨两端同时判断；禁止重复、部分或自动级联冲销。

理由：原文要求可追溯冲销，但没有给出历史成本重算规则；该方案能保证精确恢复而不重写后续业务。代价：库存继续流转后，较早单据可能无法直接冲销。“最后一次”指实际流水顺序，后续单据即使被冲销仍存在流水，不自动恢复更早单据的可冲销资格；这不是完整的逐笔撤销栈。

评审替代：允许任意历史冲销，需要定义它是按原成本补偿还是重新计算后续成本、负金额如何处理以及对未来毛利的影响。不能用一笔普通调整声称已经精确冲回原成本。这是 v0.6 最大的业务限制，应在 I2 施工前明确接受或替换。

## D4. 盘点采用保存基准、过账时检查版本的方案

建议：不长期冻结仓库。任何基准版本变化都整单拒绝，需显式刷新并复核实盘数据。零差异可过账，实盘低于占用量拒绝；盘盈成本须确认，缺成本须输入。

理由：避免旧盘点差异覆盖新业务，沿用现有乐观版本机制。代价：活跃仓库容易需要复盘；这不是不停业情况下的完整盘点方案。

评审替代：仓库冻结或盘点期间流水补偿，需要额外冻结状态/时间边界/过账规则。MVP 不默认加入这些能力。

## D5. 期初、停用与低库存口径

建议：每库存键首次业务前最多一个有效期初，已完全冲销且无其他有效业务时可重新录入。商品/仓库仍有现有量或占用时不能停用；历史业务仍可按快照查询/冲销。

min_stock_qty 当前属于商品，没有每仓阈值。建议按组织汇总该商品可用量；正阈值且 available_qty <= min_stock_qty 为候选，零阈值关闭提醒。无余额视为零，不制造虚拟库存行用于查询。暂不计算建议采购量。

评审替代：每仓最低库存应新增显式仓库商品配置，不能拿现有商品阈值当每仓阈值。本阶段优先保留 Catalog 数据模型的已有含义。

## D6. 边界、规模与维护

建议：新业务最多 200 行/单、查询最多 100 条/页，按库存键细粒度锁；不复制 Catalog 每组织写锁。RLS 不负责区分同一数据库用户内的模块；以唯一引擎写入口、代码边界检查、数据库约束及并发测试共同保护库存。

对账默认只读，重建默认 dry-run；实修复经过权限与明确范围校验，在停写窗口或相同键锁下执行，留 Audit/Outbox。不开放余额编辑 API。成本查询沿用 product.cost.read，业务动作细分权限见施工规范。

理由：沿用当前架构即可支持初始单据，避免新增微服务、队列或特权存储过程。代价：当前上限需用实际数据测量评估；大盘点按明确范围拆单，不能悄悄分批提交一张单。纯应用模块边界不等于数据库凭据泄露防护。

## 实施补充

- 0006 使用 PostgreSQL xid8 可见性快照 + 签名游标稳定分页；不引入另一套搜索存储。
- 0007 将余额修订号与事实序号分离。对账修复递增余额 `version`，让旧盘点重核；流水 `sequence` 保持连续，冲销依赖它判断实际后续操作。
- 库存写入的审计保存实际前后值；Outbox 仅携带资源 ID/版本等处理元数据。当前没有面向普通用户的 Audit 读取 API，未来增加时必须做成本权限过滤。
- D1–D6 已按授权实施。合并评审仍应确认严格末笔冲销和活跃仓库盘点需要重核这两项业务限制；改变它们应另立决策和测试，不直接改写历史成本。
