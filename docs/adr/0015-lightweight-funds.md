# ADR 0015 — 来源化往来、收付款与资金切换

状态：实施选择已确定，v0.9 正在施工，验收尚未完成。依据用户 2026-09-06 对 v0.9/v0.10 的授权及原规范中的轻量资金、金额、租户、状态、事务和过账事实要求。细则属于本阶段选择，不将未实现设计描述为已通过验收。

## 背景

v0.8 已保留采购入库、销售出库、原单退货及冲销的商业金额和库存价值。实际收付款尚未实现；旧订单金额、采购退货库存成本或销售毛利不能被当作现金及未结清余额。原规范要求业务、履约和结算状态独立。资金上线必须明确历史衔接，不能因升级自动认定所有旧业务尚未结清。

## 决策

1. **来源与现金分开。** `funds_sources` 保存 AR/AP、往来对象、冻结商业金额及原库存业务凭据。`funds_entries` 追加初始债权债务、退货冲减、原单冲销、期初转移及显式纠正。`funds_cash_documents` 和 `funds_cash_allocations` 记录实际收付及逐来源分配，`funds_cash_reversals` 追加现金冲销。此为轻量往来模块，不是会计总账。
2. **可重算余额。** 每来源余额 = 有效来源分录合计 − 有效结算分配 + 有效退款分配。正余额为待收/待付，负余额为待退款。正欠款和待退款分别汇总展示，不通过跨对象或跨来源自动净额抵销掩盖实际待处理事项。所有金额 Decimal/NUMERIC(20,4)，无自动两位舍入、容差抹零或无来源超额收付。
3. **同步业务接入。** 资金启用后，销售出库和采购入库 POST 在原事务内建立来源；退货按原单商业金额追加负额；原单冲销追加反向事实。库存、资金、Audit/Outbox/幂等同时提交或全部回滚。仓管可用原过账权限调用内部接入，回执和数量接口不因此泄露资金数据。
4. **明确切点。** `funds_activation` 是组织的显式启用记录。启用取得组织级排他事务锁，业务接入取得同键共享事务锁，即使启用行尚不存在也参与锁定。按实际锁顺序划分新旧业务，不能单凭 posted_at/now() 判断；业务日期只是明确记录的业务口径。升级不写启用记录或自动回填旧债务。
5. **历史来源化期初。** 明确录入组织、AR/AP、对象和有原因的期初余额；负期初必须显式确认是退款余额。旧有效出库/收货可绑定为历史来源，冻结有效商业净额、既有退货及已确认未结余额。正未结余额从尚未核销的同对象期初转移，转出与新来源同事务，总欠款不增加；零余额也需明确绑定。历史已结差额不计作系统本期新现金。
6. **旧单后续变化。** 没有完成来源绑定的旧出库/收货发生退货或冲销时，返回 `LEGACY_FUNDS_MAPPING_REQUIRED`，整笔原业务不提交。已绑定来源按后续商业冲减变化，超出未结部分成为待退款。不能静默漏记、自动再增加期初，或猜历史已付款。
7. **纠正与依赖。** 现金、来源分录、启用和永久回执禁止 UPDATE/DELETE，纠正追加反向事实。来源存在有效资金分配依赖时不能直接冲销；现金冲销不得使后续退款或分配成为无依据事实。原采购/销售冲销继续受既有严格末笔库存规则约束。期初和调整转移须保留相互引用，不能重复释放已转出的余额。
8. **永久去重。** 普通 Idempotency 缓存会过期；新资金命令额外保存不可变 `funds_operations` 回执。键作用域仍为组织、用户、操作、原键；权限检查先于旧回执，原键异内容冲突。过期后原意图只能回放原结果，不能再产生一张收付款或期初凭据。UI 在不确定提交期间保留原键/原内容，并支持原提交重试。
9. **锁序。** 业务 Commands 保留订单→相关凭据→资料/库存的既有锁序，进入资金时按组织、AR/AP、对象串行。纯资金写入只锁资金及必要资料，不反向排他锁定业务订单/库存。资金读取在需要多次查询时按同一对象共享锁保证汇总和明细一致。
10. **结算独立展示。** 来源的 UNPAID/PARTIAL/PAID 依据已过账义务及有效结算计算，待退款另有状态和余额。订单详情的资金摘要只覆盖实际过账来源并受对应资金读取权限控制；未启用、历史映射不完整或尚无实际来源时，不提供伪造的 UNPAID。是否关闭订单、是否全量发货/收货不由结算状态决定。

## 边界和接口

单张收付款只允许一个 AR/AP 方向及同一对象，1–100 个唯一来源分配，金额必须为正并不超过当前同方向额度。类型 SETTLEMENT/REFUND 与 AR/AP 共同决定收款、付款、客户退款、供应商退款；不执行银行转账。预览在服务端校验并计算合计，正式提交再次校验，预览不占用余额。

启用/期初/调整/收付/退款/冲销分别授权。余额和来源读取按 `funds.ar.read`、`funds.ap.read` 区分；前端不凭现有销售/库存权限推断可以读取资金。后台核心资金 Commands 不能交由 Celery 延迟成功。

所有新业务表 FORCE RLS，角色 forge_app 无超级用户或 BYPASSRLS，引用使用复合租户外键。往来对象的 nullable customer/supplier 分支需明确非空约束，不能让 SQL CHECK 的 NULL 三值逻辑绕过对象引用。错误、日志、Outbox 和最小回执不泄漏别租户或无权读取的金额。

## 待验收及需复核选择

四位金额、单币种 CNY、无自动超付/跨来源净额抵销、显式启用及来源化期初、永久最小命令回执均为本阶段有意选择。正式采用历史资料前需要核对期初金额；开发升级不会代替这个业务核对。

通过条件：来源/现金对账、零及负余额、退货/退款/反向事实、历史映射、重复与 TTL 后回放、跨租户/权限、并发和 COMMIT 故障、空库/真实旧资料升级、实际页面及当前提交 CI，逐项见[资金验收清单](../funds-v0.9-acceptance.md)。
