# ADR 0016 — Catalog 正式导入的逐行事务与永久执行记录

Status: Proposed for v0.10；规范已整理，尚未实施。用户授权资金v0.9后继续运营v0.10，业务施工必须等待v0.9验收。ADR0015保留给资金；本ADR不改变Catalog/库存/销售/采购/资金事实语义。

依据：[原导入设计](../import/catalog-import-design.md)、[运营v0.10规范](../operations-v0.10.md)、[验收清单](../operations-v0.10-acceptance.md)及权威迁移上下文的租户、Command、Decimal、Audit/Outbox要求。

## 背景

现有Catalog已有10种资源的Pydantic输入、确定性校验、组织级写锁、事务内Audit/Outbox和幂等。商品创建还通过同一Command自动生成基础单位换算。导入若绕过这些入口，将产生另一套校验及事实写入路径。

原设计已经规定单批一种资源、先预览、显式更新、逐行事务、失败重试和源码行号。普通幂等记录默认24小时到期，不能用它证明某个导入行永远未执行。10,000行整批大事务会长时间持锁，也不能给用户真实的部分完成结果。

现有Redis/Celery可以调度工作；embedding关闭时产品Outbox事件保留pending，现有轮询前100条可能持续被其占据。导入进度不能依赖该事件队列的模型处理结果。

## 决策

| 决策 | 本阶段选择 | 含义 |
|---|---|---|
| I1 范围 | 10种现有Catalog资源，每批一种；自然键定位，不导入业务单据 | 复用现有资料模型，不提供任意SQL/通用表导入 |
| I2 输入 | xlsx受限ZIP/XML解析，保留原始单元格词法值，Decimal直接读取XML数值 | 编码必须文本；数字编码不猜前导零；不执行公式/宏/外链 |
| I3 预览 | 原值/清洗值/动作/目标版本/引用版本/分类模板版本持久保存，整批无错误后显式确认 | 预览不是授权或锁，默认不覆盖现有资料 |
| I4 更新 | 显式更新模式，未映射字段保持原值，冻结最终完整Command输入 | 不以schema默认值擦除资料；保持基础单位/关联不变量 |
| I5 依赖 | 引用必须已存在于当前组织，同文件新增引用分批处理 | 避免隐式创建分类、单位、供应商；新商品先基础单位再换算/默认包装 |
| I6 事务 | 每行一次现有write_command，业务+成功行状态+Audit/Outbox同事务 | 行成功必须已COMMIT，整个文件可以部分完成 |
| I7 去重 | import_rows成功状态/目标ID永久保留；行幂等键另作短期回放 | TTL、清理、消息重复、worker重启不二次创建成功行 |
| I8 调度 | Celery独立轮询数据库持久批次；DB行锁协调，Redis只唤醒 | 不依赖embedding Outbox队头，不把队列结果当事实 |
| I9 身份 | 确认时绑定认证操作者；每行重查组织/用户active与当前权限 | 后台不以SYSTEM提升权限；会话结束不撤销已明确确认任务，账号/权限变更会阻断后续行 |
| I10 保留 | 原xlsx不长期落盘；原/清洗正文上传后7天清理；摘要、成功状态及审计本版不自动删除 | 过期禁执行；清理不破坏永久去重或业务事实 |

openpyxl用于结构与xlsx输出，defusedxml用于受限底层XML读取，python-multipart用于现有FastAPI上传接入。通过uv声明依赖并生成锁文件，不引入云文件存储、独立服务、消息基础设施或新数据库。文件解析、解压和Python3.14兼容性必须有实际测试。

## 表及状态约束

`import_batches` 保存 organization_id、资源、创建/执行操作者、文件名/哈希、版本、状态、创建/确认/过期时间及摘要。`import_rows` 保存 organization_id、batch_id、源行号、动作、定位信息、冻结输入与版本、状态、目标ID/版本、错误、尝试次数与审计关联。

两表启用并强制RLS，批次/行/操作者关联使用复合租户外键。成功行的身份、动作、哈希、目标和成功状态不能被普通更新或正文清理重置；正文清理只置空允许到期删除的字段。若目标资源类型决定无法建立单一SQL外键，由Application在同租户Command结果内写入，并以类型约束及来源回归验证，不开放客户端目标ID写入。

批次确认冻结内容；相同确认键不同内容冲突。成功行不可重试，过期批次不可重启；普通失败可以按原冻结内容重试，版本冲突需要新预览。已成功行不能因批次摘要更新或失败记录写入而回退。

## 一行的提交边界

1. 在forge_app租户事务内锁定可执行行，确认批次已授权且未过期，成功则直接读取结果。
2. 从已确认的操作者重新加载权限和active状态，不相信文件字段或早先权限快照。
3. 在既有Catalog组织事务锁内重查冻结目标/引用/分类模板版本，调用原write_command。
4. 同事务记录成功状态、目标ID、来源关联，COMMIT成功后反馈进度。
5. 失败使该行全部回滚；另开事务记录错误前重新读取行状态。如果提交结果不明或其他worker已经成功，不能把成功标成失败或重新执行。

永久成功状态是处理重送的首个判断，但授权必须先执行；不能借旧成功回执读取已撤权价格。工作进度只返回最小回执，敏感原文读取另作当前权限过滤。

并发worker可使用行锁和SKIP LOCKED；不跨行保持业务事务。不能先持有批次锁等待Catalog锁，再在业务提交时反向等待批次锁。批次汇总在行提交后处理或读时聚合，计数不是业务事实。进程中断会释放行锁、回滚未提交行；轮询重新检查状态后恢复。

## 保留和下载

原xlsx只使用受限上传临时文件，关闭即释放。原值、清洗值、引用验证正文、详细错误在上传7天后清理；期限、到期状态和剩余未执行量在界面明确显示。清理与行执行串行，不能清掉正在提交所需内容。

成功行最小标记、目标来源、批次摘要和既有Audit不随幂等TTL或正文清理删除。过期内容不可再下载或执行。下载需导入读取权限及该资源读取权限，价格/联系资料不能从错误详情绕过授权；Outbox与日志只保存有限元数据。

## 替代方案及代价

- 整文件大事务：与逐行部分完成要求冲突，10,000行会延长锁持有和重试范围。
- 直接COPY/INSERT业务表：绕过Command、基础换算、版本保护和Audit/Outbox，拒绝采用。
- 只保存Celery状态或短期幂等回执：无法证明消息重复或TTL之后是否已提交，拒绝采用。
- 每次失败自动刷新版本：会把用户已经修改的资料再次覆盖，拒绝采用；需要重新预览。
- 文件永久保存或引入对象存储：超出首版所需，增加保留与运行边界；使用受限短期正文和永久最小结果。

## 需要复核的明确选择

7天正文期限、更新时未映射字段保持、同文件新引用分批处理、创建者确认/重试身份、永久最小成功标记属于本阶段实现选择。补货的组织范围、30日净销量、7日复核周期和静态分支详见运营规范；它们不借本ADR改变交易Command或把建议自动变成采购确认。

目前仅完成规范；需要真实文件、逐行故障、并发worker、TTL/清理、撤权、跨租户及浏览器结果证明这些决定被正确实现。
