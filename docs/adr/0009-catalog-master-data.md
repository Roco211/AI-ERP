# ADR 0009 — Catalog master data and commands
Status: Accepted implementation of user-approved v0.5 plan

Catalog contains categories, brands, units, products, product units and prices. Customer, supplier and warehouse remain distinct master-data resources; no inventory or document transactions are introduced. Each tenant table uses FORCE RLS, composite tenant foreign keys, uuidv7 IDs and explicit application filtering. All mutation routes invoke named application commands with permissions, Idempotency-Key, Audit and Outbox in one transaction. No physical-delete API. Status changes use activate/deactivate commands; edits require expected_version and stale edits return DOCUMENT_VERSION_CONFLICT.

SKU is tenant unique. Barcode is tenant unique when present. Supplier product codes are unique within a supplier. Product prices are authoritative in ProductPrice; product read models expose standard/retail/wholesale as derived fields rather than duplicate writable stores. Customer-exclusive price is explicit; no fabricated historical transaction price. Price tier fallback is deterministic.

Every product unit stores a direct positive Decimal factor to its product's base unit. Base factor is exactly one. Existing base units cannot change. Future documents receive frozen conversion snapshots (unit_id, qty, factor, base_qty); this milestone implements the value object only, not document tables. Changing a factor requires the old version and never mutates existing snapshots.

Category attributes are a small versioned JSONB template (text, decimal, enum, boolean), not a general schema designer. Product writes validate against the current template; template changes are rejected if they invalidate existing products. Category-parent changes serialize per organization and prohibit cycles.

Implementation details requiring review: all Catalog mutations serialize per organization using one transaction advisory lock, then row locks/version checks; appropriate for initial master-data volume and consistent category-template validation. This limits concurrent master-data writes within one organization and can be refined with deterministic entity locks after load measurements. Prices are always in the product's base unit; dedicated tier/customer resolution excludes transaction-history fallback until transactions exist. Activation revalidates references. Deactivation does not cascade to dependents; inactive references cannot be newly selected. Base/default/in-use supplier conversion rows cannot be deactivated. Code uniqueness is case-sensitive; search is case-insensitive.
