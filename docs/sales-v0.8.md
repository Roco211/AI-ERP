## 1. 目标与边界

打通客户→价格建议→销售订单→确认占用→一次/分批出库→实际成本和毛利→原单退货。继续使用当前模块化单体、同源/api、RuntimeContext、Cookie Session、PostgreSQL RLS、Audit/Outbox/幂等及InventoryEngine。

冻结Python3.14/FastAPI/Pydantic v2/SQLAlchemy2/Alembic/psycopg3/PostgreSQL18+pgvector/Redis/Celery/uv，Next.js App Router/React/TypeScript/shadcn Base UI/Tailwind/TanStack Query/Table/RHF/Zod/pnpm。浏览器不使用JS Number计算业务金额，服务端Decimal/NUMERIC为权威。不引入新基础设施或框架大版本。

本阶段不做应收、收款、退款、会计凭证、税费/发票、折扣/运费分摊、赊销额度、复杂审批、报价单、多仓拆单、超发、欠货确认、AI开单或自动补货。销售金额不等于已收款；暂不生成UNPAID等没有资金事实支持的结算状态。原规范的资金状态保持未来独立接入的位置。

## 2. 必须保持的业务事实

- 订单草稿不改变现有量、占用量或成本。
- 确认订单增加reserved_qty，on_hand_qty不变；available=on_hand-reserved。
- 出库POST减少on_hand，消费属于该订单的reservation；生成不可变流水并记录实际出库成本。
- 占用、释放也产生专门流水，base_qty=0，成本不变；Reservation和Balance可以从流水重建。
- 禁止负库存和超额占用；数据库保护0≤reserved≤on_hand。
- 移动加权平均成本由InventoryEngine计算；出库按当时均价，全出扣清剩余库存金额和尾差。
- 单据历史单位/数量/因子/金额/成本快照不能随资料或均价变化重算。
- 所有副作用与Audit/Outbox/幂等在同一事务提交；沿用function scope，在返回HTTP成功之前COMMIT。

## 3. 订单与占用（建议S1）

单客户、单发货仓、每商品一行，最多200行。单位可以不同于基础单位，但必须存在有效直接换算。确认时全量占用全部行；任一商品可用量不足，则整张订单保持DRAFT，不做部分确认或自动占用未来采购量。

| Command | 前置 | 结果与库存 |
|---|---|---|
| Save/UpdateDraft | 有效客户/仓库/商品/单位；版本正确 | DRAFT；保存价格与换算快照；不改库存 |
| Confirm | DRAFT，资料/换算仍有效，所有行可用库存足够 | CONFIRMED；逐行建立来源占用；全事务成功或全部回滚 |
| Cancel | DRAFT，或CONFIRMED且有效出库量为零；必填原因 | CANCELLED；释放全部剩余占用；已有出库草稿不能再POST |
| Close | CONFIRMED；必填原因 | CLOSED；释放未发部分占用；停止新出库；不伪改履约状态 |

不自动关闭已全量出库订单，不提供CLOSED/CANCELLED重开。确认后商业内容不可改删；变更需求通过关闭未发部分、另开订单。关闭/取消用于释放既有义务，允许客户或单位后来停用；不得因资料停用而把库存占用永久锁住。

订单业务状态DRAFT/CONFIRMED/CLOSED/CANCELLED；履约状态UNFULFILLED/PARTIAL/FULFILLED单独计算。有效出库是POSTED且未冲销的出库，不扣减销售退货。全部行未发为UNFULFILLED，全部达到订购量为FULFILLED，其余PARTIAL。退货量单列，不自动重开待发，也不新增占用。

分别显示：订购量、有效已发、原订单未发、累计已退、剩余占用、当前可执行出库量。CLOSED即使原订单未发量>0，可执行出库量也为0，剩余占用必须为0。销售员不能把其他订单的占用转给本单。

## 4. 出库、退货与冲销（建议S2–S4）

### 分批出库

出库从单一CONFIRMED订单创建，关联原订单行，继承客户、仓库、商品、单位、换算因子及最终销售单价；不在出库单改价。草稿不再占用库存或消耗额度。POST在订单锁及库存键锁内重查原订单状态、有效已发、当前剩余占用；不能累计超发，也不能仅凭仓库总库存绕过本单占用。

订单确认后单位因子更改，不改变后续出库快照。新出库要求相关资料有效；历史取消/关闭/合法冲销按历史快照操作。业务只读状态不能解除过账保护。

销售出库行保留本次原单位数量、base_qty、销售金额、实际出库成本和毛利。库存实际成本来自本次ISSUE流水的负value_delta，包含引擎全出尾差；不能拿当前均价回算历史毛利。数量比较用基本单位。

### 原单退货

退货必须引用原POSTED销售出库行，退回原仓、原客户、原商品、原单位，累计有效退货≤原实发。退货不恢复订单待发量，不创建新的订单占用；补发另开订单。关闭订单后可以接收符合条件的退货。

建议退货销售冲减金额按原出库销售价格，退货库存价值按原出库实际成本分摊，均在服务端计算。设原行qty=Q、销售金额=A、实际成本=C，本次退q：普通部分退货销售冲减为round(q×原单价,4)，成本回收为round(C×q/Q,4)；各自最后一次退完取原总额减之前有效退货总额，确保两种金额分别归零。不能先把C/Q舍入成六位单价后乘回。部分舍入若超过剩余销售金额或剩余成本，明确拒绝精度冲突，不截断。

该成本回收作为准确入库金额交给InventoryEngine，参与当前库存移动平均；退货不是恢复历史均价的冲销。引用的出库单价/成本不可由客户端覆盖。原出库成本为零时退货成本也为零；负毛利允许如实展示，不擅自增加低价销售审批政策。

### 冲销

销售出库和退货状态沿用DRAFT/POSTED/REVERSED，POSTED不可改删、不回DRAFT。沿用ADR0012严格末笔整单冲销：每个受影响库存键都没有后续流水，后续占用也算依赖；后续单已冲销不使更早单自动可冲销。

出库冲销：原单仍POSTED、无有效关联退货、订单仍CONFIRMED；恢复原数量/价值/前均价，并恢复被消费的原订单占用，恢复该单可发额度。订单已CLOSED/CANCELLED时拒绝出库冲销，避免恢复悬空占用或悄悄重开已关闭订单。

退货冲销：符合严格末笔和库存约束时扣回原退货数量/价值、恢复之前均价及可退额度；不改变销售订单占用/履约。与普通库存、采购单据一样，不支持部分、历史级联或自动重算后续成本。

## 5. 客户价格与单位（建议S5）

确定性优先级：客户专属价 → 客户最近有效成交价 → 客户价格等级 → 商品标准价。当前Catalog的ProductPrice是每基本单位价格，不能把原字段改成每箱价格。成交历史只取有效POSTED销售出库，排除草稿、仅确认订单和已冲销出库；退货单不成为新成交价来源。即使原成交后来全部退回，它仍是未冲销的真实成交记录，默认保留在历史价中并显示退货信息。

销售报价接口接收已解析的customer_id/product_id/unit_id，不接收organization_id。目录价格转所选销售单位时，price=base_price×current_factor；历史价转所选单位时，用原销售单位单价×current_factor/original_factor，内部精度50，只在最终所选单位单价舍入至6位，不提前舍入中间基本价。返回来源类型、资料或出库ID、原单位/原因子、目标单位/因子、报价和舍入说明。

正报价若舍入成0，返回PRICE_PRECISION_CONFLICT；缺价返回明确unset，不把空值当零。显式零价和人工改价允许，但必须可见且留审计。

草稿行分AUTO/MANUAL两种定价方式：AUTO在保存草稿时由服务端解析并保存来源/金额；MANUAL保存显式单价并标记人工输入。客户端不能伪造来源字段。界面先展示报价，再展示保存后的服务端单据金额供确认；报价与保存之间价格发生变化，以保存结果为准并显式提示。确认冻结最近一次已保存的商业价格，不暗中重新定价；若要重报，显式更新草稿后再确认。

更换草稿客户时，界面清空上个客户的报价选择并要求复核，不能静默沿用其专属价。历史单位因子变化只影响新报价，不改旧销售单。

输入数量/单价为Decimal字符串，最多6位；金额4位，ROUND_HALF_UP，内部精度至少50，沿用20,6数量/价格和20,4金额上限。qty×factor必须可用6位基本数量精确表达，不悄悄舍入库存数量。单据总额为服务端行金额之和。

## 6. 毛利与权限（建议S6）

毛利只来自有效已过账业务：销售出库金额减实际出库成本，再扣除有效退货的销售冲减金额减成本回收金额。订单草稿/确认金额不算已实现毛利。订单详情可列有效销售额、有效成本、净额和净毛利；这不是会计利润表或收款统计。不做关账期间或历史时点快照，单据冲销后按当前有效事实重算。

| 能力 | 服务端权限 | 价格 / 成本 |
|---|---|---|
| 数量列表/详情/占用来源 | sales.read | 默认不携带敏感价格/成本 |
| 报价、成交价、销售金额 | sales.read + product.price.read；报价同时校验客户/商品查看权限 | 可见销售价格，不能由此看到成本 |
| 保存/编辑订单 | sales.order.write + product.price.read | 可确认交易条款，不要求成本权限 |
| 确认订单 | sales.order.confirm + product.price.read | 全量占用；无成本泄露 |
| 取消/关闭订单 | sales.order.cancel / sales.order.close | 释放义务不要求成本读取 |
| 出库 / 退货POST | sales.ship / sales.return | 可由只看数量的仓管执行；金额由冻结来源计算 |
| 冲销 | sales.reverse + 对应sales.ship或sales.return | 服务端使用原事实；成本仍按读取权限剔除 |
| 查看成本与毛利 | sales.read + product.price.read + product.cost.read | 缺任一敏感读取权限不返回毛利或可反推成本的汇总 |

创建/修改出库、退货草稿分别需sales.ship/sales.return；任何额外读取仍独立授权。UI隐藏不是权限校验。每次命令先检查当前动作权限，再访问幂等回执；撤权后旧键不能绕过。回执仅返回id/status/version/request_id。无成本权限时，列表、详情、汇总、历史、错误、导出和未来Audit接口均不可泄露成本或毛利。当前不新增普通用户Audit读取接口。

## 7. 数据和引擎接入（建议S7）

模块建议 `modules/sales/{domain,application,api}`，前端 `features/sales/`，接入现有 `/sales` 导航。新migration从0008追加，计划0009_sales（以实施时唯一head为准）；本规格增量不创建或执行migration。

建议增加sales_orders、sales_order_lines、sales_documents、sales_document_lines；所有新业务表organization_id、FORCE RLS、租户复合外键、有限数字约束。销售订单与库存单据附属表保留强来源，不复制库存余额或另建一套流水。

确认创建内部SALES_RESERVATION凭据及不可变行快照，只记录RESERVE/RELEASE来源，不能被界面当作实物出库单。内部凭据POSTED表示占用建立；后续关闭/取消追加RELEASE事实，不改写凭据。出库/退货类型为SALES_SHIPMENT/SALES_RETURN。通用库存和采购Command必须拒绝销售类型，不提供手工创建、修改或冲销内部占用凭据的公开路由。

现有Engine要求消费行ID=占用来源行ID，销售出库不能直接复用这一假设。建议在库存行追加可空的reservation_source_line_id及租户自引用外键，由销售Command从冻结订单来源填写；出库行消费独立占用行时，引擎验证占用行、商品/仓库键、租户及命令能力全部匹配。既有非销售路径保留同来源校验。API/AI输入不得提交reservation_id或reservation_source_line_id。

销售附属表将订单行、内部占用行、出库行、原出库退货行关联；约束及应用共同拒绝跨订单/客户/仓库/商品/租户引用。所有销售库存变化仅经InventoryEngine；对账必须覆盖独立来源行的RESERVE→ISSUE→RELEASE及冲销重放。

## 8. 事务、并发与错误

保持非特权forge_app与RuntimeContext，租户不来自客户端。锁序：幂等锁 → 销售订单头锁 → 关联库存凭据/原单头锁（ID排序）→ 客户、仓库、商品、单位和换算共享锁（统一表序及ID序）→ InventoryEngine按(warehouse,product)库存键锁 → reservation锁 → 业务/Audit/Outbox/幂等 → 一次COMMIT。

取消/关闭和出库必须在同订单锁下串行，既不能先读剩余占用后在锁外释放，也不能先锁库存再反向拿订单锁。独立订单仍可在不同库存键上并发；同键竞争受可用量限制。Catalog停用/因子更新与确认/出库交叉测试。出库/退货任一行或流水、余额、Audit、Outbox、幂等、提交阶段失败都回滚；Redis/worker不参与核心成功判定。

错误沿用Problem Details/request ID，明确区分INSUFFICIENT_STOCK、INSUFFICIENT_RESERVATION、OVER_SHIPMENT、OVER_RETURN、INVALID_SOURCE、DOCUMENT_VERSION_CONFLICT、UNIT_CONVERSION_CHANGED、PRICE_PRECISION_CONFLICT、RETURN_QUOTE_CHANGED和REVERSAL_DEPENDENCY_CONFLICT。错误不输出价格/成本或别租户资料。提交结果不确定时沿用原键原body重试；业务状态和版本独立防止旧幂等记录过期后重复过账。

## 9. API与工作台

REST前缀 `/api/v1/sales`：orders列表/详情/保存草稿/confirm/cancel/close；shipments/returns创建；documents列表/详情/修改草稿/post/reverse；price-quote、price-history；订单详情提供受权限控制的毛利汇总。所有输入通过Pydantic/OpenAPI生成TS，不手写并行DTO。

工作台：销售订单、销售出库、销售退货、客户成交价；毛利在授权详情中展示。ProductPicker键盘选品和单位选择、RHF/Zod表单、TanStack Query/Table沿用现有实现。订单显示现有/占用/可用、已发/待发/已退；确认提示本次全量占用；关闭提示释放未发占用。

价格来源可点开追溯；保存后的服务端金额再供确认。仓管只有数量时，照常能按来源单据处理出库/退货。异步详情按ID隔离，旧响应不能覆盖当前单据；锁定重复点击和不确定提交期间的字段；冲突支持重新加载复核。库存流水来源能跳回销售原单。

页大小≤100（UI25），每单≤200行；价格历史按posted_at/id/line稳定排序且分页；单据列表筛选客户、状态、日期/关键字需有限输入。390像素界面不产生整页横向溢出。性能仅报告实际测量，不以分页限制冒充生产容量保障。
