## 1. 目标与边界

交付三个可连续使用的业务流程：Excel 资料预览与正式导入；确定性补货建议与采购草稿；按权限查看经营概览及其来源。沿用模块化单体、现有登录、RuntimeContext、RLS、业务 Commands、Audit/Outbox、OpenAPI→TypeScript 和 ERP shell。

冻结 Python 3.14/FastAPI/Pydantic v2/SQLAlchemy 2/Alembic/psycopg3/PostgreSQL 18/Redis/Celery/uv，Next.js App Router/React/TypeScript/shadcn Base UI/Tailwind/TanStack Query/pnpm。数值使用 Decimal/NUMERIC；前端展示服务端结果，不以 JavaScript Number 计算金额、换算或建议采购量。Excel 解析所需应用依赖通过 uv 正常生成锁文件，不能手工改锁文件。

不做交易单据批量导入、库存数量直接导入、资金事实导入、自动确认采购/收货、供应商自动下单、跨仓自动调拨、需求预测模型、BOM/MRP、完整 BI、会计报表、云服务或 AI 工具。已有本地 embedding 不参与这三个流程的正确性或完成条件，不改变其开关和业务含义。

## 2. 正式 Catalog 导入

### 2.1 资源及自然键

每个批次只处理一种现有资源，不新增第二套主资料写入规则。

| 资源 | 导入定位键 | 引用 / 特殊字段 |
|---|---|---|
| Category | 分类编码 | 父分类编码；属性模板 JSON 按现有 AttributeDefinition 校验 |
| Brand | 品牌编码 | 名称、备注 |
| Unit | 单位编码 | 名称、备注 |
| Customer | 客户编码 | 联系资料、现有价格等级枚举 |
| Supplier | 供应商编码 | 联系资料 |
| Warehouse | 仓库编码 | 名称、地址、备注 |
| Product | 商品编码 SKU | 条码另作唯一性检查；分类/品牌/基础与默认单位/首选供应商编码；属性列 |
| ProductUnit | 商品编码 + 单位编码 | 明确的直接换算率 |
| ProductPrice | 商品编码 + 价格类型 + 客户编码（适用时） | 每基础单位价格，沿用客户专属/等级价语义 |
| SupplierProduct | 供应商编码 + 商品编码 | 供应商货号另作唯一性检查；采购单位编码、lead_days |

模板一资源一种结构；价格、换算不混入商品表形成第二份事实。每次上传明确选择资源和一个数据工作表；有多个可选数据工作表而未指定时拒绝猜测。其他工作表不会自动导入，但整个工作簿仍接受安全检查。

引用必须在当前组织已存在且有效；首版不解析同一文件内新建行之间的引用。父分类先导入，再导入子分类；新商品先使用基础单位，导入其 ProductUnit 后，再显式更新默认采购/销售单位。商品 Command 自动生成的基础单位换算沿用现有行为，不要求用户另导一条重复基础换算。

### 2.2 文件与数值

- 仅接受未加密 `.xlsx`；上传内容最多 10,000,000 字节，选定工作表最多 10,000 条非空数据行、64 列。行数依据实际单元格解析，不相信工作表声明的 dimension。
- 解压后所有成员累计最多 100,000,000 字节，单成员最多 50,000,000 字节，最多 1,024 个 ZIP 成员；单成员解压/压缩比例超过 100 时拒绝。流式读取持续核对实际字节数，不能仅信任 ZIP 目录声明。
- 拒绝宏、公式（包括有缓存结果的公式）、加密文件、外部关系/链接、嵌入对象、危险路径、重复 ZIP 成员、DTD/外部实体和损坏结构。拒绝非法文件时无业务写入，不执行 Excel、宏、公式或网络请求。
- 原始 xlsx 只在上传请求的受限临时生命周期内存在；请求结束关闭并删除临时文件，不进入公开目录、长期文件存储或数据库文件列。文件名仅保存受限显示值，不用作路径。
- 单价、数量、换算和数字属性从原始 XML 单元格词法值构造 Decimal；不得先经 Python float，再调用 str/Decimal 修补精度。文本数值与 XML 数字均要符合原 API 精度、范围和有限值规则，拒绝日期、布尔冒充数值和不合法格式。
- SKU、条码及所有引用编码必须是文本单元格。Excel 数字、科学计数法、日期格式或自定义数字显示格式不能证明原始编码完整，返回 `UNSAFE_IDENTIFIER_CELL` 并指导改为文本；不猜回前导零或被 Excel 截断的长编码。数值型条码即使看似整数也不自动接受。
- 原值、规范化值分列保存。仅去除首尾空白/全角空格、统一显示用乘号；SKU/条码不改大小写，不自动合并近似名称。空价格是未设置，不能变成零；显式零按现有 API 规则处理。
- 导出模板、预览及错误结果时，用户文本以文本单元格写入；以 `= + - @` 开始的文本不得变成公式。未知列、重复列、禁用系统字段、未知属性键都明确报错。

采用 openpyxl 处理工作簿结构和模板/结果输出，底层 XML 数值由 defusedxml 与受限 ZIP 读取取得原文；上传使用 FastAPI 的受限文件接口及 python-multipart。三者属于应用解析依赖，不引入服务或更换框架；Python 3.14 安装、锁文件和边界测试通过后方可认定可用。

### 2.3 预览与显式更新

导入页显示资源、文件、工作表、源行号、原值、清洗值、拟执行动作、定位对象及错误代码/中文原因，服务端分页。默认只新增；发现现有自然键或条码/供货货号冲突时拒绝覆盖。用户显式选择更新模式后重新预览，服务端记录目标 ID、expected_version、引用 ID/版本及分类模板版本。

目标和引用均从认证租户内的编码解析，文件不接受 organization_id、actor/user ID、业务状态、版本、数据库 ID、search_text 或幂等键。更新不能改基础单位或关联关系，继续接受原 Command 的不可变字段约束；未映射的可选字段在更新时保持原值，明确空值才按模板约定清空可空字段。预览必须显示最终完整更新值，不能借 schema 默认值悄悄清掉原字段。

同文件重复自然键、非空条码、供应商货号和价格组合键一律报错，不使用“最后一行覆盖”。近似大小写编码只提示，不改现有大小写敏感语义。分类模板的未知键、必填、枚举、decimal/boolean 均按现有规则校验。

整份预览有任何错误时不允许确认执行；预览不持有跨请求事务、数据库锁或执行授权。确认冻结批次内容及其哈希，不能在已确认批次上直接改行。业务冲突需要新预览；可从失败行生成待修正文件或新批次，但不能复制成功行再次执行。

错误至少区分 `REQUIRED`、`UNKNOWN_REFERENCE`、`INVALID_ATTRIBUTE`、`INVALID_DECIMAL`、`UNSAFE_IDENTIFIER_CELL`、`DUPLICATE_IN_FILE`、`EXISTING_CODE`、`VERSION_CONFLICT`、`REFERENCE_CHANGED`、`PREVIEW_EXPIRED`、`PERMISSION_DENIED` 和文件边界错误。

### 2.4 执行、事务与恢复

新增 `import_batches` 与 `import_rows`，两表均 FORCE RLS、组织复合外键并仅由 forge_app 在认证范围操作。批次保留资源、创建/执行操作者、文件名/哈希、版本、状态、有效期、计数；行保留源行号、动作、定位键/目标 ID、冻结版本、原值/清洗值、引用快照、执行结果、错误及尝试次数。来源审计可定位 batch/row，不能把原文件或联系/价格数据放进 Outbox payload、结构化日志。

逻辑状态：预览错误或可确认 → 待执行/执行中 → 全部成功、部分失败、全部失败或授权阻断；超过期限且还有未执行行时为过期。每行独立区分待执行、成功、失败及未执行原因，批次计数必须与行状态一致。状态通过显式 Commands 推进，不提供通用状态 CRUD。

确认和失败重试需 `catalog.import.write` 及资源对应写权限；批次查看/结果下载需 `catalog.import.read` 及对应资料读取权限。价格批次还需 `product.price.read`，写入需 `product.price.write`；撤回敏感权限后不能从旧预览/错误下载读回价格。首版仅批次创建者确认和发起重试；同组织其他获授权用户可查看，不自动接管其执行身份。

使用现有 Celery 定期扫描数据库持久化待执行批次，Redis 仅提供调度。不能把 `.delay()` 成功当成提交事实，也不能依赖 product embedding 的 Outbox 消费进度；模型关闭或产品事件队头阻塞时，导入仍可完成。需要枚举待执行租户时采用已有 worker 同类的最小只读租户发现能力，不授予绕过业务 RLS 的写权限。

每行执行遵循：

1. 开启新的 forge_app 租户事务；锁定待执行行，重查其持久状态，成功行立即跳过。
2. 按批次已确认的操作者重新加载组织/用户 active 状态及当前权限，构建后台 RuntimeContext；不得使用预览时保存的权限集合。显式确认的任务可跨登录会话继续，账号停用或撤权会阻断尚未执行的行。
3. 在既有 `catalog-write:<organization>` 事务锁内检查目标版本、引用状态/版本、分类模板版本及冻结内容。发现变化明确失败，不悄悄刷新 expected_version 或按新模板改写行。
4. 调用 `catalog.application.service.write_command`，使用 batch ID + row ID + action 构成稳定幂等键，沿用所有业务校验、基础换算创建、Audit 和 Outbox。
5. 同一事务写成功行状态、目标 ID/版本及最小结果回执；COMMIT 后才把该行计为成功。任一环节失败，整行回滚。记录失败另开事务并再次检查未被其他执行者成功提交，不能覆盖成功状态。

允许多个 worker 通过行锁/跳过已锁行协调，但不能在持有批次锁时等待业务 Catalog 锁、再反向等待该批次锁。批次摘要在行事务之后更新或读取时聚合。worker 中断、消息重复、租约过期或数据库重连后先读持久行状态，禁止重新创建成功资料。

24 小时幂等记录不是永久执行证明；成功行状态及目标 ID 是导入永久去重依据，清理幂等记录后仍不能重复行。数据库在 COMMIT 阶段丢失响应时，同样先查询行状态再决定恢复。

前端只轮询持久批次状态；断网或刷新后从批次列表恢复。失败重试只选择失败行，成功行不可选，尚未执行行由原批次恢复。旧版本/引用变化不能通过“重试”自动覆盖；修正需新预览。结果明确说明逐行事务及部分完成，不声称文件级原子成功。

### 2.5 保留与清理

批次原始/清洗单元格、验证快照和详细行错误保留上传后 7 天。到期后禁止新的执行/重试，清理可恢复业务正文；活动行事务与清理串行，不删除尚在同一事务执行的数据。已经成功的行永久保留最小状态、源行号、动作、内容哈希、目标 ID/版本、操作人和审计关联；批次摘要和既有审计事实继续保留。这里的永久保留是本版本不设置自动删除，不延伸为完整合规保留策略。

过期后列表显示摘要及成功来源，正文显示已到期，不提供空白原文冒充完整预览。清理不能删除成功去重标记、业务资料、Audit、Outbox 或历史交易快照。

## 3. 确定性补货

### 3.1 统计范围与参数

沿用现有 `inventory.queries.low_stock` 的全组织、商品基础单位汇总口径。本阶段不把商品级 min_stock_qty 默认为每仓阈值；推荐页明确“全组织库存”。创建采购草稿时再由用户选择实际收货仓。原低库存查询与其语义保留。

以查询时刻为 `as_of`，销售窗口取业务时区过去 30 个完整日，排除尚未结束的当日。业务时区来自部署配置，默认 Asia/Shanghai，API/页面明确展示；不从服务器或浏览器的隐式本地时区猜测。使用窗口起点包含、终点不包含的 UTC 时间界限查询。

| 符号 | 定义 |
|---|---|
| V | 当前各仓 `sum(on_hand_qty - reserved_qty)`；无余额行按 0；不混用现有量与可用量 |
| O | CONFIRMED 采购订单的未到基础数量合计；每行订购量减有效 POSTED 收货量；DRAFT/CANCELLED/CLOSED 不纳入 |
| N | 窗口内有效 POSTED 销售出库基础数量，减窗口内有效 POSTED 销售退货基础数量；各按自身 posted_at 入窗口 |
| D | `max(N, 0) / 30`，不提前舍入；负净量显示原 N 和净零说明，不能形成负补货 |
| S | 现有 Product.min_stock_qty 作为本算法的安全库存基线 |
| B | 现有 Product.reorder_qty，作为出现真实缺口时的最低单次建议量；不代表箱规、MOQ 或库存目标 |
| L | 有效首选供应商、该商品有效 SupplierProduct 的 lead_days；显式 0 合法，缺关系为未配置，不能装作 0 |
| H | 固定复核周期 7 天，本阶段不增加预测或自动参数优化 |

采购退货不重开订单待收量，因此 O 不加回退货；100 件订单有效收货 25、退货 10，O 仍为 75。跨租户、无效订单、内部占用凭据和库存调拨都不能计作销售或在途采购。

### 3.2 公式与零值规则

有销售速度且 L 已配置时：

```
reorder_point = S + D * L
target_stock  = S + D * (L + 7)
inventory_position = V + O
gap = max(0, target_stock - inventory_position)
candidate = V <= reorder_point
suggested_base_qty = ceil_to_6_decimals(max(B, gap))
    仅当 candidate 且 gap > 0；否则为 0
```

D=0 或 L 未配置时采用明确的静态分支：`reorder_point = target_stock = S`，其余规则相同。D=0 时 days_of_stock 为 null，附“无历史”或“期内净销量为零”原因；不除零、不声称无限覆盖。L 未配置时附“缺供货提前期，仅按安全库存计算”，进入草稿前必须复核供应商和单位。

D>0 时 `days_of_stock = V / D`，仅用于说明当前可用库存覆盖天数；O 已纳入建议数量，但不能被描述成已经可用的库存。S=0、D=0 且 V=O=0 时建议为 0，显示缺少销量和安全库存依据；B 本身不能触发无依据采购。

候选阈值使用 <=；候选的建议量仍可因在途已覆盖目标而为 0，并明确说明。只在最终基础数量处向上取 6 位小数，不把中间日均销量舍入后再计算。超出既有数值上限时报错，不静默封顶。

| 验收输入 | 预期 |
|---|---|
| 30 日出库 90、退货 30；S=10，B=20，L=5，V=8，O=6 | N=60，D=2，阈值20，目标34，在途位置14，gap20，建议20，覆盖4天 |
| 上例 O=30 | 在途位置38，建议0，说明在途覆盖；可用量仍8 |
| 上例 V=21、O=0 | 可用量高于阈值20，不建议采购，即使低于目标34 |
| N=0，S=10，B=20，V=3，O=2 | 静态 gap5，建议20；覆盖天数null |
| N=-5，S=0，B=100，V=O=0 | D=0，建议0，保留净量-5并说明，不能因B自动补100 |
| N=1，S=B=0，L=1，V=O=0 | 目标8/30，建议0.266667；不能先把日均舍入后计算 |
| N=60，L未配置，S=10，B=20，V=8，O=6 | 静态目标10已覆盖，建议0，显示提前期缺配置，不套用动态目标34 |

### 3.3 接入采购草稿

只读建议返回 as_of、窗口、算法版本、输入值、原因、基础单位建议量及首选供应商信息，支持有界筛选/分页。查询使用一致的数据库快照汇总，避免余额、销量与在途来自不同提交时刻；不取得长时间库存排他锁。

用户选择商品、供应商、收货仓、采购单位及逐行价格，服务器生成并展示采购草稿预览。一次只生成同供应商、同仓的一张采购订单，最多沿用现有 200 行。缺价不变为零价；显示可用历史参考和人工输入来源，最终金额由现有 `purchasing.application.orders.save` 决定。

创建前重新读取建议依据、资料/换算及报价；若数量依据或用户确认的建议快照已变，返回明确冲突并要求刷新复核，不静默改量。所选单位必须有当前有效直接换算；基础建议量无法精确表示为合法采购数量时，要求选择基础单位或显式修正数量，不猜整数箱规/订货倍数。用户手工调整数量允许，但须展示服务器计算结果并留业务原因。

创建动作复用采购 DRAFT Command、同事务 Audit/Outbox 和幂等，不确认订单，不创建收货，不改变库存或资金。补货创建记录须能追溯算法版本、查询快照哈希和目标采购单；同一创建请求并发、响应丢失或幂等缓存过期后均不能重复建单。新一轮明确复核后的独立采购属于新业务意图。

建议读取需 `replenishment.read` 以及 catalog.read/inventory.read/sales.read/purchase.read/supplier.read，且不返回进价或成本。生成草稿另需 `replenishment.create`、purchase.order.write 与 product.cost.read。隐藏按钮不替代这些服务端授权。

## 4. 经营概览

### 4.1 日期统计和当前余额分开

替换 `/dashboard` 占位，提供日期范围、业务时区、as_of 和来源链接。首版范围最多 366 日，服务器做有界聚合和分页；不在浏览器下载所有单据求和。

- **期间业务卡片：** 指定窗口内有效已过账销售出库金额、销售退货冲减、净销售、实际净成本及已实现净毛利。按各单自身 posted_at 选取，毛利口径复用 sales.queries 的不可变实际成本；草稿/仅确认订单不算成交。
- **期间资金卡片：** 实际收款、实际付款、客户退款、供应商退款分别展示，按 v0.9 资金单据的业务日期筛选及其有效/冲销规则计算。期初欠款和历史来源绑定不算本期实际现金；净额必须同时展示其组成和方向。
- **当前余额卡片：** 当前应收、应付、待退款、库存估值、低库存商品数和补货候选数。它们是 as_of 当前余额，不跟随日期范围伪装成某个历史日的余额；界面分区并明确“当前”。

沿用 v0.8 的当前有效 POSTED 事实口径，后续合法冲销会使历史窗口查询按当前有效事实重算。不给历史时点结账快照或不可追溯的“会计利润”。实际成本事实缺失时返回不可用状态，不按0造出毛利；销售金额沿用逐出库行4位金额，不从订单金额或当前商品价重算。

无资金权限不返回资金字段；资金尚未启用或历史期初映射尚不完整时，按 v0.9 状态说明不可用/范围，不把缺来源当作零余额。日期范围外退货不扣本窗口销售，但全时段业务净额必须能与现有销售查询对账；同一规则在卡片和钻取列表一致。

### 4.2 权限、查询和界面

新增 dashboard.read 仅提供概览入口，不授予底层业务数据权限。销售数量需 sales.read，销售额另需 product.price.read；成本与毛利还需 product.cost.read。库存估值需 inventory.read 与 product.cost.read；资金指标需 v0.9 已验收的相应读取权限；补货指标需完整补货读取权限。

无权限指标不返回数值、变动比例、图表点或可反推出金额的组合；不能以0占位。每张卡片提供相同条件下的来源列表/查询，来源明细继续执行原权限及租户校验。客户端缓存即使已有数值，权限变化后也立即遮蔽。

首版提供指标卡片、最多按日的期间净销售/收付趋势及来源钻取；图表使用服务端小数串的展示结果，任何业务合计在服务端完成。不新增会计科目、财务报表、自动经营结论或定时 AI 简报。

聚合在一次只读一致性快照内完成；关联采用明确租户键和有界 CTE，避免逐订单调用 order_detail 导致 N+1，也避免销售/退货/资金多表直接联结而乘倍求和。资金 v0.9 数据结构稳定后再写适配查询，不能在本规范阶段假定其未实现表结构。
